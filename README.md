# Mini Script — Week 1 Day 3

## 1. Day 3 실습 목적

Day 3에서는 단일 Python 스크립트를 작성하는 수준을 넘어,
코드를 **서비스 관점에서 재사용 가능한 구조**로 정리하는 것을 목표로 했다.

구체적으로는 다음을 경험한다.

- 실행 코드와 비즈니스 로직의 분리
- TypedDict 기반 타입 계약을 유지한 채 코드 구조 리팩토링
- pytest를 통한 최소 테스트 도입
- Git 기반 실무 워크플로우(브랜치 → PR → squash merge) 유지

이 단계는 이후 FastAPI, 배치 작업, SQL 기반 집계로 확장하기 위한
**전환 지점**에 해당한다.

## 3. 타입 분리 → 테스트 도입까지의 흐름

### 1️⃣ 타입을 계약으로 정의

- `TypedDict`를 사용해 입력(`Review`)과 출력(`AggregatedStats`) 구조를 명확히 정의
- 타입은 문서가 아니라 **정적 계약**으로 취급
- mypy를 통해:
  - 필드 누락
  - 타입 불일치
  를 실행 전에 차단

### 2️⃣ 집계 로직을 순수 함수로 유지

- `aggregate_reviews`는:
  - 입력 → 출력만 존재
  - print, assert, I/O 없음
- 내부 구현 변경과 무관하게
  **외부 계약만 유지되면 안전**

### 3️⃣ pytest로 계약 고정

- 테스트는 “정답 검증”이 아니라 **현재 동작을 명시적으로 고정**
- 작성한 테스트:
  - 정상 집계 케이스
  - 빈 입력 리스트 처리
  - 의미적으로 잘못된 rating 값에 대한 현재 동작 문서화
- assert를 실행 코드에서 제거하고 테스트로 이동

이로써 리팩토링 시 변경 가능성을 확보했다.

## 4. 이 코드가 서비스로 가면 어디에 쓰일지

이 코드는 다음 형태로 자연스럽게 확장될 수 있다.

- **FastAPI Service Layer**
  - API 요청으로 받은 리뷰 데이터를 집계
- **Batch / ETL 작업**
  - 로그 데이터를 주기적으로 집계
- **SQL 집계 결과 후처리**
  - DB에서 GROUP BY 한 결과를 Python에서 재가공

즉, 현재 코드는
- “연습용 스크립트”가 아니라
- **실제 서비스 코드의 최소 단위**

로 설계되어 있다.

## 5. Git & 협업 워크플로우

- 모든 작업은 브랜치 기반으로 진행
- 변경 사항은 PR로 관리
- squash merge로 히스토리 정리
- 커밋 메시지는 작업 단위 기준으로 작성

이 과정을 통해,
코드 변경 → 문서화 → 검토 → 병합까지의 흐름을 하나의 사이클로 완주했다.
